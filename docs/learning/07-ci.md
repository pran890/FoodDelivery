# Step 07 — CI

> **Topic:** Continuous Integration with GitHub Actions: build and test every change on a clean Linux machine, with package caching.

## Why this matters for this project
Tests help only if someone runs them. Until now that was one Windows laptop, with its own SDK, package cache and case-insensitive file system. CI runs the same checks on a **fresh Linux machine** for every change, and Linux is where the containers will run from Step 57. Experiment 4 shows a change that builds here and breaks there.

## Concepts

### 1. Vocabulary
| Term | Here |
|---|---|
| **Workflow** | `ci.yml`, a YAML file in `.github/workflows/` |
| **Event** (trigger) | A push to `main`, or any pull request |
| **Job** | `Architecture` and `Kitchen`: each on its own fresh machine, in parallel |
| **Step** | One command (`run:`) or one reusable action (`uses:`) |
| **Runner** | The machine: `ubuntu-24.04`, with Docker preinstalled (Testcontainers needs it) |
| **Matrix** | One job definition, run once per entry. A new test project is two more lines. |

Jobs share nothing. Both compile the whole solution again, which costs some seconds and keeps the file simple. It also means a project without tests still has to compile.

### 2. Caching, and what it's worth
```yaml
key: nuget-${{ runner.os }}-${{ hashFiles('global.json', 'Directory.Packages.props', '**/*.csproj', '**/Directory.Build.props') }}
restore-keys: nuget-${{ runner.os }}-
```
- **The key is a hash of everything that decides which packages we need.** Same inputs, same cache.
- **A cache is never changed once saved.** A new key makes a new cache.
- **`restore-keys`** is the fallback: on a miss, take the newest cache with that prefix and download only what's missing. Seen in experiment 4, where one `.csproj` changed.
- **Scope:** a cache made in a pull request is visible to that pull request only. One made on `main` is visible to all.
- Both jobs try to save the same key, so one logs "Unable to reserve cache". That's harmless.

Measured, in seconds:

| | Load cache | Restore | Save | Total |
|---|---|---|---|---|
| Architecture, no cache | 0 | 15 | 5 | **20** |
| Architecture, with cache | 6 | 8 | 0 | **14** |
| Kitchen, no cache | 0 | 13 | 3 | **16** |
| Kitchen, with cache | 12 | 8 | 0 | **20** |

**The cache hardly helps.** Loading 724 MB takes about as long as downloading the packages, and one job got slower. These are single runs, so treat them as a rough picture. The lesson is to **measure a cache before trusting it**. It stays for now because it's this step's topic, and it makes builds depend less on NuGet being reachable.

### 3. Is it really reproducible?
Not completely. `global.json` says `10.0.401` with `rollForward: latestFeature`, which means "this version **or newer**". CI used **10.0.404**, while the laptop has 10.0.401. A newer SDK can bring new analyzer rules, and with warnings as errors that can turn CI red with no code change. `rollForward: disable` would pin it exactly, at the price of everyone installing that exact SDK.

### 4. A workflow is code with access to your repository
The repository is **public**, so anyone can open a pull request that runs this workflow.

| Protection in `ci.yml` | Why |
|---|---|
| `permissions: contents: read` | The token can read the repo and nothing else |
| Actions pinned to a commit hash | A tag such as `v7` can be moved to other code; a hash can't |
| `persist-credentials: false` | The token isn't left on disk for later steps (including code from the pull request) |
| `pull_request`, **not** `pull_request_target` | The second runs with the base repo's permissions and secrets: dangerous with someone else's code |
| No secrets at all | Nothing to steal |
| `timeout-minutes: 15` | The default is 6 hours, and a hung container would use all of it |

### 5. Cancelling outdated runs
```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```
In a pull request only the newest commit matters, so a newer push cancels the older run. On `main` nothing is cancelled, so every commit there keeps its own result.

## Trade-offs and alternatives
| Choice | Why here | Alternatives |
|---|---|---|
| GitHub Actions | Free for public repos, next to the code | GitLab CI, Azure Pipelines, Jenkins (self-hosted) |
| Linux runner | Same OS as deployment, Docker included | A Windows runner as well: closer to the laptop, but no Linux containers |
| Build in both jobs | Simple | One build job that uploads its output: worth it when builds get slow |
| `actions/cache` with our own key | Works with central package management | `setup-dotnet`'s built-in cache, which needs `packages.lock.json`. Lock files would also pin transitive packages. |
| Pinned hashes | Safe | Tags: easier to read and update. Dependabot can update the hashes. |
| Nothing blocks a merge yet | Single developer | A branch ruleset that requires green checks. Not configured. |

## Break-it experiments
All were run on GitHub, in [pull request 1](https://github.com/pran890/FoodDelivery/pull/1). To repeat them, use a branch and a draft pull request so that `main` stays green.

### 1. Break a test and see the pipeline go red (the roadmap's experiment)
In [InfrastructureTests.cs](https://github.com/pran890/FoodDelivery/blob/step-07-ci/tests/FoodDelivery.Sandbox.Kitchen.Tests/InfrastructureTests.cs), expect `4` instead of `3`, and push.
→ **Kitchen: fail** (`Expected: 4, Actual: 3`), **Architecture: pass**. The second job still ran because of `fail-fast: false`.
Locally, `.\tools\ci.ps1` on the same change stops with `FAILED: Test tests/FoodDelivery.Sandbox.Kitchen.Tests` and exit code 2.

### 2. Cold cache vs warm cache
Run the same commit twice (`gh run rerun <id>`). The first logs "Cache not found", the second "Cache hit". The table in concept 2 has the times.

### 3. A style warning fails the build
Add `using System.Text;` to the Waiter's `Program.cs` and push.
→ both jobs fail at **Build**: `error IDE0005: Using directive is unnecessary`. The tests never run.

### 4. Works on my machine
In the Waiter's `.csproj`, write the reference in lower case: `fooddelivery.servicedefaults.csproj`.
→ **Windows: Build succeeded. CI: red.** On Linux that file doesn't exist, so `Polly` and `Resilience` can't be found.
The real cause is easy to miss: `MSB9008: The referenced project ... does not exist` is only a **warning**, even though warnings are errors here. The errors you see first are the consequences.

### 5. Two quick pushes
Push, then push again within about 15 seconds.
→ the older run ends as **cancelled** after 22 s and the newer one succeeds.

### 6. The same test on Linux and Windows
`Dead_postgres_fails_readiness_but_not_liveness` takes **97 ms** on the Linux runner and about **2.5 s** on the laptop. That confirms Step 05's note about slow refused connections on Windows.

- The time limit, and pull requests from forks.

## Interview questions

**1. What's the difference between CI, continuous delivery and continuous deployment?**
CI: every change is merged often, built and tested automatically. Delivery: every green change *can* be released at the push of a button. Deployment: every green change *is* released, with no manual step.

**2. How do you choose a cache key?**
Hash every input that determines the content (lock files, central versions, project files) and include the OS. Too broad a key serves stale content, too narrow a key never hits. Add a prefix fallback for partial hits, and measure whether the cache saves time at all.

**3. Why pin third-party actions to a commit hash?**
A tag can be moved. If an action's repository is compromised, the attacker can point `v7` at malicious code that runs in your pipeline. A hash always means the same code. Tools such as Dependabot keep hashes current.

**4. What's dangerous about `pull_request_target`?**
It runs in the context of the base repository, with its secrets and possibly a writable token, even for pull requests from forks. If the workflow then checks out and runs the pull request's code, a stranger's code runs with your secrets.

**5. A build is green locally and red in CI. Where do you look?**
At the differences: file name case, path separators, line endings, time zone and culture, SDK version, uncommitted files, cached packages, environment variables, and timing on slower machines. Then reproduce it in a clean container.

**6. How would you speed up a slow pipeline?**
Measure each step first. Then parallelise independent jobs, build once and share the output, run only the tests a change affects, cache what's slow to *produce* rather than to download, and fail fast with the cheap checks first.

**7. What do you do about flaky tests in CI?**
Treat them as bugs. Automatic retries hide real races. Quarantine the test visibly with an owner, find the shared state or timing assumption (Step 06), fix it, and bring it back.

**8. How do you keep secrets safe in CI?**
Use as few as possible. Prefer short-lived credentials (OIDC federation) to stored keys, limit them to protected environments, never expose them to fork pull requests, never print them, and give the token the least permissions.

**9. Why run on Linux if the team develops on Windows?**
Because production runs on Linux. Differences such as case sensitivity show up in CI instead of after a deployment.

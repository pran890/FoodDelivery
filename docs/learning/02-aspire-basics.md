# Step 02 — Aspire basics

> **Topic:** describing a distributed system in code (the Aspire AppHost), running it with one command, and letting services find each other **by name** (service discovery).
> **Tag when approved:** `step-02-aspire-basics`

> **Since Step 12** the Sandbox (Kitchen and Waiter) is gone. Its links below lead to this step's tag, and to run its experiments check out `step-02-aspire-basics`.

## Why this matters for this project
We'll run 10 services plus Postgres, Redis, RabbitMQ and Mailpit. Without an orchestrator, every service needs hard-coded URLs and ports (`http://localhost:5072`) in its config. You'd start each one in a separate terminal, in the right order, and update every caller whenever a port changes. Aspire replaces that with:
- **One file describing the system:** [AppHost.cs](../../src/AppHost/FoodDelivery.AppHost/AppHost.cs).
- **One command to start it all**, plus a dashboard.
- **Name-based addressing:** Waiter calls `https+http://kitchen`, and no port ever appears in service code.

## How to run it
```powershell
cd D:\FoodDelivery
dotnet run --project src\AppHost\FoodDelivery.AppHost
```
The console prints a **Dashboard** link with a login token (`https://localhost:17073/login?t=...`). Open it. Stop everything with **Ctrl+C**; Aspire stops every process it started.
Because the AppHost project sets `<AspireUseCliBundle>true</AspireUseCliBundle>`, `dotnet run` goes through the Aspire CLI bundle. That's why the output looks like *"Trusting certificates… Connecting to AppHost… Starting dashboard…"* rather than plain ASP.NET logs.

## Concepts

### 1. The AppHost and the app model
The AppHost is an ordinary .NET console app. `DistributedApplication.CreateBuilder` gives you a builder where you declare **resources**: anything Aspire manages. That can be a .NET project (`AddProject`), a container (`AddContainer`, `AddPostgres` in Step 03), an executable, or a parameter or secret. Each resource has a **name** (`"kitchen"`), which is how the dashboard labels it and how other services address it.
```csharp
var kitchen = builder.AddProject<Projects.FoodDelivery_Sandbox_Kitchen>("kitchen");
builder.AddProject<Projects.FoodDelivery_Sandbox_Waiter>("waiter")
    .WithReference(kitchen)   // give waiter kitchen's addresses
    .WaitFor(kitchen);        // start waiter only after kitchen is running
```
`Projects.FoodDelivery_Sandbox_Kitchen` is a **source-generated** type. The AppHost SDK creates one for every `<ProjectReference>` in the AppHost `.csproj` (dots become underscores), so a typo is a compile error, not a runtime surprise.

The AppHost doesn't run your services itself. It hands the model to **DCP** (Developer Control Plane), a separate orchestrator process (`dcp.exe`). DCP starts the processes and containers, watches them, and runs **proxies** in front of them (concept 4). The dashboard is another process the AppHost starts.

### 2. `WithReference`: wiring is configuration
`WithReference(kitchen)` injects kitchen's endpoints into waiter as **environment variables**:
```
services__kitchen__https__0 = https://localhost:7148
services__kitchen__http__0  = http://localhost:5072
```
.NET configuration turns `__` (double underscore) into `:` (the section separator), so inside Waiter this is the config section `services:kitchen:https:0`. Waiter's `/debug/discovery` endpoint prints exactly that. You can also see the variables in the dashboard: **Resources → waiter → Environment variables**.

Step 03 uses the same mechanism for databases: `WithReference(postgres)` injects `ConnectionStrings__identity=...`.

`WaitFor(kitchen)` holds waiter back until kitchen reaches the *Running* state. From Step 05, once health checks exist, `WaitFor` waits for **healthy**, not just started.

### 3. Service discovery: resolving a name on each request
In [Extensions.cs](../../src/ServiceDefaults/FoodDelivery.ServiceDefaults/Extensions.cs):
```csharp
builder.Services.AddServiceDiscovery();                                          // register resolvers
builder.Services.ConfigureHttpClientDefaults(http => http.AddServiceDiscovery()); // add a handler to every HttpClient
```
Waiter's typed client sets `BaseAddress = new Uri("https+http://kitchen")`. On each request, the service discovery handler in the `HttpClient` pipeline rewrites the URL:
- `kitchen` is the **service name**, looked up in configuration (`services:kitchen:*`).
- `https+http` means **prefer https, fall back to http** if the service has no https endpoint. Plain `https://kitchen` would *only* accept https; `http://kitchen` only http.
- If no configuration matches, the resolver **passes the name through to DNS**. That's why experiment 3A fails with `No such host is known. (kitchen:443)`. In Kubernetes, `kitchen` *would* be a valid DNS name for a Service, so the same code works there without the variables.

**Service discovery is just configuration plus a resolver.** Nothing magic: experiment 3B runs Waiter *outside* Aspire, sets one environment variable by hand, and it works.

### 4. The DCP proxy: the launchSettings ports aren't the app's ports
While the system runs, `netstat` shows:

| Port | Owned by |
|---|---|
| 7148, 5072 (Kitchen's `launchSettings.json`) | **dcp** |
| 7240 (Waiter's `launchSettings.json`) | **dcp** |
| 16494, 16496 (random) | Waiter, Kitchen (the real apps) |

DCP listens on the stable ports from `launchSettings.json` and **proxies** to each app, which Aspire starts on a random port. Kitchen still reports `listeningOn: https://localhost:7148` because the proxy forwards the original `Host` header.

**Why a proxy?**
- Callers get stable addresses even when an app restarts on a new port.
- It makes **replicas** possible: `.WithReplicas(2)` runs two Kitchen processes behind one address.

**Gotcha (experiment 5):** the proxy balances **per TCP connection, not per HTTP request** (Layer 4, not Layer 7). `HttpClient` keeps connections alive and reuses them, so Waiter stuck to *one* replica for all its calls. Fresh connections (separate `curl` runs) spread across both. Real per-request balancing needs a Layer 7 balancer. Our YARP gateway (Step 17) and Kubernetes ingress are Layer 7.

### 5. The dashboard (what you'll see now and what's still empty)
- **Resources:** each resource's state (Running, Exited, Waiting), endpoints, environment variables, and Start/Stop/Restart buttons.
- **Console:** each process's stdout.
- **Structured logs, Traces, Metrics: empty for now.** The template's OpenTelemetry setup was removed on purpose, so nothing reports to the dashboard yet. Step 04 adds it, and you'll see those tabs fill up.

### 6. What isn't automatic
If Kitchen crashes, Aspire **does not restart it**. The dashboard shows *Exited*, the proxy port closes, and Waiter's calls fail with 500 until you press Start (experiment 4). Aspire is a development orchestrator, not a production supervisor. Restarting crashed processes is Kubernetes' job (Step 58).

## Trade-offs and alternatives
| Choice | Alternative | Why we didn't (for local development) |
|---|---|---|
| Aspire AppHost | Docker Compose | Compose runs everything as containers, so every code change means rebuilding an image (slow, and more RAM). Aspire runs .NET services as normal processes (fast edit-run, debugger attaches) and only infrastructure as containers. Compose is still used for deployment (Step 57). |
| Aspire AppHost | Running each service by hand + `appsettings` URLs | No single view, manual start order, hard-coded ports drift between services. |
| Config-based service discovery | A registry (Consul, Eureka) | A registry is another always-on component (RAM, ops). Config + DNS fallback covers local development and Kubernetes. |
| Client-side resolution (the caller resolves the name) | Server-side (the caller hits a load balancer/DNS name, the infrastructure routes) | We get both: config locally, DNS/Service in Kubernetes. Code stays `https+http://kitchen` either way. |
| Cut-down ServiceDefaults | Keep the full template | The full template mixes 4 topics into one step. Adding each in its own step keeps every `git diff` about one idea. |

## Break-it experiments
All of these were run while building this step; the outputs are real. Undo each change afterwards.

### 1. Move Kitchen to another port and change nothing in Waiter
In `src/Sandbox/FoodDelivery.Sandbox.Kitchen/Properties/launchSettings.json`, change `7148` to `7150`. Run the AppHost and call `GET https://localhost:7240/debug/discovery` →
```json
{"services:kitchen:http:0":"http://localhost:5072","services:kitchen:https:0":"https://localhost:7150"}
```
`GET https://localhost:7240/order` still works, and `listeningOn` is now `https://localhost:7150`. Waiter's code and config didn't change.

### 2. Forget `WithReference`
Comment out `.WithReference(kitchen)` in `AppHost.cs` and run it. `/debug/discovery` → `{}`, and `/order` → **500**. Waiter has no idea where `kitchen` is.

### 3. Run Waiter outside Aspire
With the AppHost running (so Kitchen is up), start a second Waiter by hand:
```powershell
$env:ASPNETCORE_URLS = "http://localhost:5299"
$env:ASPNETCORE_ENVIRONMENT = "Development"
.\src\Sandbox\FoodDelivery.Sandbox.Waiter\bin\Debug\net10.0\FoodDelivery.Sandbox.Waiter.exe
```
- **A (no discovery configuration):** `GET http://localhost:5299/order` → **500**, with this in the console:
  ```
  System.Net.Http.HttpRequestException: No such host is known. (kitchen:443)
  ```
  No configuration, so the name went to DNS, and `https+http` picked https, hence port 443.
- **B:** stop it, then set **one** variable and start it again:
  ```powershell
  $env:services__kitchen__https__0 = "https://localhost:7148"
  ```
  `/order` now works. That one line is all Aspire does for discovery.

### 4. Kill Kitchen
`Stop-Process -Name FoodDelivery.Sandbox.Kitchen`. Then `/order` → **500**. The dashboard shows Kitchen as *Exited*, port 7148 stops listening, and **nothing restarts it**. Press **Start** on Kitchen in the dashboard and `/order` works again.

### 5. Two Kitchens: Layer 4 vs Layer 7 balancing
Change the kitchen line in `AppHost.cs` to `AddProject<...>("kitchen").WithReplicas(2);` and run it. Two Kitchen processes start.
- 6 calls through **Waiter** (`/order`): all 6 say the **same** pid. Waiter's `HttpClient` reuses one kept-alive connection.
- 6 separate `curl.exe -s https://localhost:7148/dish-of-the-day` runs (a new connection each time): both pids appear (we saw 2 and 4; random, not strict alternation).
- 6 requests in **one** curl run (`curl.exe -s url url url url url url`, one connection): all the same pid again.

So DCP's proxy balances **connections**, not requests.

## Interview questions

**1. What is .NET Aspire and what problem does it solve? Is it for production?**
An opinionated stack for building and running distributed .NET apps. Its core is the **AppHost**: a C# model of the system's resources (services, databases, brokers) and their relationships, which it runs locally with one command, plus a dashboard for logs, traces and metrics. It removes hand-wired URLs, start-order scripts and per-service observability setup. In production it isn't the runtime: the app model can be **published** to deployment targets (Compose, Kubernetes manifests, Azure Container Apps), and the services run there. `ServiceDefaults` (telemetry, health, resilience, discovery) does run in production, because it's just library code in each service.

**2. AppHost vs ServiceDefaults?**
The AppHost is a separate project that **describes and orchestrates** the system; it isn't deployed with your services. ServiceDefaults is a shared library **every service references** and calls (`builder.AddServiceDefaults()`), holding cross-cutting startup wiring: service discovery, OpenTelemetry, health endpoints, HttpClient resilience. One configures the environment; the other configures each process.

**3. How does service discovery work in Aspire, end to end?**
`WithReference(x)` makes the AppHost inject `services__x__{endpoint}__{index}` environment variables. In the service, `AddServiceDiscovery()` registers resolvers, and `AddServiceDiscovery()` on the HttpClient builder adds a handler. A request to `https+http://x/...` is rewritten per request by looking up `services:x:https` (else `http`) in configuration. If nothing matches, the name goes to DNS. Because the source is ordinary configuration, it can come from env vars, appsettings, Key Vault and so on.

**4. Client-side vs server-side service discovery?**
**Client-side:** the caller resolves the service name to instance addresses (from a registry or config) and picks one. Examples: Eureka + Ribbon, Aspire's resolver. The client controls balancing, but every client needs the logic. **Server-side:** the caller hits one stable name (load balancer, Kubernetes Service DNS) and infrastructure routes to an instance. Simpler clients, but an extra hop and component. Aspire's model works with both: config-based locally, DNS/Service in Kubernetes.

**5. Why `https+http://` rather than `https://`?**
It's a **scheme preference list**: use the https endpoint if the service has one, otherwise http. Plain `https://` fails if only http exists, which is common inside a cluster where TLS ends at the ingress. The preference list lets the same code run against https locally and http-only internally. `ServiceDiscoveryOptions.AllowedSchemes` can restrict this, e.g. https only in production.

**6. Why do Aspire's environment variables use double underscores?**
.NET configuration uses `:` for hierarchy (`services:kitchen:https:0`), but `:` isn't valid in environment variable names on every OS. The environment-variable configuration provider maps `__` to `:`, so `services__kitchen__https__0` becomes `services:kitchen:https:0`. The same applies to `ConnectionStrings__Default` or `Logging__LogLevel__Default`.

**7. You run 2 replicas behind a proxy, but one replica gets all the traffic. Why?**
The proxy balances at **Layer 4** (per TCP connection), and the client reuses one long-lived connection. `HttpClient` pools and keeps connections alive, and HTTP/2 multiplexes everything over one. Every request rides the same connection to the same backend. Fixes: a **Layer 7** balancer that routes per request (YARP, Envoy, a Kubernetes ingress), client-side balancing across resolved endpoints, or limiting connection lifetime (`SocketsHttpHandler.PooledConnectionLifetime`) so connections get rebalanced.

**8. What do `WithReference` and `WaitFor` each do?**
`WithReference` is about **addressing**: it injects connection info (endpoints, connection strings) so the dependent can find the dependency. `WaitFor` is about **start order**: the dependent doesn't start until the dependency is Running, or Healthy once health checks exist. You usually want both. `WithReference` alone can start a service before its database accepts connections; `WaitFor` alone starts it in order but without the address.

**9. Aspire or Docker Compose for local development?**
Compose: everything is a container, it's close to production and language-agnostic, but you rebuild an image for every code change and debugging is harder. Aspire: services run as normal processes (fast inner loop, debugger, hot reload), infrastructure as containers, typed C# wiring, built-in dashboard and telemetry. The cost is .NET-centric tooling and a dev/prod gap. Common split, and ours: Aspire for the inner loop, Compose or Kubernetes for deployment.

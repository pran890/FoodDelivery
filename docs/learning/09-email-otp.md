# Step 09 — Email OTP

> **Topic:** signing in with a one-time code sent by email, and why each small defence around a 6-digit number is needed.
> **Tag when approved:** `step-09-email-otp`

## Why this matters for this project
This is the front door of the whole app: there are no passwords, so the email code is the only proof of who someone is. A 6-digit code has just 1,000,000 possibilities. The number itself protects nothing; the rules around it do.

## The Redis layout
As approved:
```
otp:{email}    hash    mac       32 bytes, HMAC-SHA256(key, "otp:v1:{email}:{code}")
                       attempts  integer, starts at 0
               expires 300 s after it was issued
```

## Concepts

### 1. One defence per attack
| Attack | Defence | Test that fails without it |
|---|---|---|
| Try all codes | 5 attempts, then the code is deleted | `After_five_wrong_guesses_...` |
| Send 100 guesses at once | Count atomically, before comparing | `Of_100_simultaneous_guesses_...` |
| Wait and try later | 5-minute expiry, never extended | `An_expired_code_...` |
| Replay a code | Deleted on success, by exactly one request | `A_code_works_once`, `Of_simultaneous_correct_requests_...` |
| Read Redis | HMAC instead of a hash | (experiment 3) |
| Copy a stored value to another account | The HMAC includes the email | `A_stored_mac_is_worthless_...` |
| Learn who has an account | Same answer, same code path | `Known_and_unknown_emails_...` |
| Learn why a code failed | One answer for every failure | `Every_failure_gets_the_same_answer` |
| Predict the code | `RandomNumberGenerator` | none: randomness can't be tested this way |
| Measure the comparison | `FixedTimeEquals` | none |

11 deliberate bugs were put in one at a time, and all 11 were caught: no attempt limit, a sixth guess, no `EXISTS` check, no expiry, never deleted, ignoring who deleted it, a MAC without the email, a different answer for a missing code, a failed email becoming an error, an unhandled duplicate user, and Redis reported as Unhealthy. **Not tried:** treating known emails differently, guesses extending the expiry, and a plain hash instead of the HMAC.

### 2. Why HMAC and not a hash
With only a million inputs, a plain hash can be reversed by trying them all. Measured: **all 1,000,000 SHA-256 values in 442 ms**. A salt doesn't help, because it's stored next to the hash. An HMAC needs a **secret key that isn't in Redis**, so someone who steals the Redis data learns nothing.

For passwords you'd use a slow hash (Argon2, bcrypt). For six digits even a slow hash is only a matter of time.

The key is generated by the AppHost and kept in its user secrets. Changing it only invalidates codes that are still waiting.

### 3. Count first, then compare
```
wrong:  read attempts → compare → add 1      100 requests all read 0, so all 100 get compared
right:  add 1 → allowed? → compare           each request gets its own number
```
The "add 1 and check" is one **Lua script**, which Redis runs as a single step. It checks `EXISTS` first. Without that, `HINCRBY` on an expired key creates a new key **that never expires** (measured: TTL `-1`).

### 4. Single use under concurrency
Two requests with the right code both compare as equal. Who wins is decided by the *delete*: a second script deletes the key only if `mac` is still the one we compared, and only the request whose delete succeeded is signed in. The condition also protects a *newer* code from being deleted.

### 5. No hints
- **Request:** always 202. There's no database lookup at all, so known and unknown emails take the same path. A different *duration* would also be a hint.
- **Verify:** wrong, expired, used up, never requested, missing: all `400 Invalid or expired code.`
- **A failed email is still 202,** because the failure could depend on the address. It's logged, without the code or the email.

### 6. Degraded is not Unhealthy
Without Redis nobody can sign in, so it's tempting to report Unhealthy. But from Step 12 Identity also serves the public keys every other service needs. Taking it out of rotation would turn "can't sign in" into "nothing works". So Redis is **Degraded**: visible, still 200, still receiving traffic. Postgres stays Unhealthy.

### 7. Redis memory
- The container cap is 128 MB; Redis itself is limited to **96 MB**. A full Redis then refuses writes with an error, instead of being killed by Docker.
- **`noeviction`**: codes are data, not a cache (experiment 6).
- Aspire has no setting for this, so the AppHost sends `CONFIG SET` when Redis is ready. **If Redis is restarted without the AppHost, the limit is gone** (measured: `maxmemory 0`) until the AppHost runs again.

## Trade-offs and alternatives
| Choice | Why here | Alternatives |
|---|---|---|
| Email code | No passwords to store or leak | Magic link (easier, but mail scanners click links), passkeys (strongest), TOTP app |
| Redis | Expiry built in, atomic scripts | A Postgres table: durable, but you clean up and lock yourself |
| Lua scripts | Atomic in one round trip | `MULTI` can't decide based on a value it reads. `WATCH` can, with retries. |
| New request replaces the code | Simple, matches what users expect | Keep the old one until it expires |
| Send inside the request | Simple | A queue (Step 51): faster answer, retries, survives a crash |
| One generic error | No hints | Specific errors: friendlier, but leak information |

## Known gap until Step 10 (closed there: [10-rate-limiting.md](10-rate-limiting.md))
Nothing limits how often a code can be *requested*. Each new code brings 5 more guesses, and anyone can flood an inbox. Local use only until rate limiting exists.

## Break-it experiments
All were run while building this step. **Undo each change afterwards.**

### 1. Brute force, and expiry (the roadmap's experiments)
Request a code, then send 5 wrong ones.
→ five times `400`, and after the fifth the key is gone (`EXISTS` = 0). The **right** code now also gets `400`.
For expiry: request a code, `EXPIRE otp:<email> 1`, wait 2 s, send the right code → `400`, and no key is left behind.

### 2. Count non-atomically
Replace the script in `TakeAttemptAsync` with: read `attempts`, return if it's 5 or more, then `HashIncrementAsync`.
→ `Of_100_simultaneous_guesses_only_five_are_compared` fails, 3 of 3 runs: attempts 6, 7, 8, … get through.

### 3. Reverse a hash
Hash a random 6-digit code with SHA-256 and try all codes.
→ found in under a second (442 ms for all one million). The same search against an HMAC without knowing its key: **0 matches**.

### 4. Use a code twice
→ the second time is `400`. Five correct requests at once, held back with `CLIENT PAUSE ... WRITE` so they really overlap: exactly **one** 200.
Make `VerifyAsync` ignore whether the delete worked → that test fails.

### 5. Stop things
| Stopped | Request a code | `/health` |
|---|---|---|
| Mailpit | **202** (after about 4 s) | Healthy |
| Redis | **503** "Sign-in is temporarily unavailable." after **5–6 s** | **Degraded**, 200 |

When Redis is back, the next request works.
The 5 seconds are the Redis client waiting for a reconnect. `BacklogPolicy.FailFast` would fail at once, at the price of an error on every short blip.

### 6. Fill Redis
On a throwaway Redis limited to 3 MB, store 10 codes and then 20,000 other keys:

| Policy | Writes | Codes left |
|---|---|---|
| `noeviction` | about half fail with `OOM command not allowed` | **10 of 10** |
| `allkeys-lru` | all "OK" | **0 of 10** |

Identical in 3 runs each. With eviction nothing reports an error; people just can't sign in.
In the app, a full Redis gives **503**, and no key is written.
(A first attempt filled Redis from *inside* a Lua script and everything was accepted: Redis checks the limit only when a script starts.)

### Worth knowing: every request took 2.15 s
Windows again (Step 05). Mailpit listens on `127.0.0.1` only, and `localhost` tries `::1` first: **refused after 2.2 s**, then connected in 0 ms. Local and Windows only.

### Not verified
Traces and logs in the dashboard, and a mail server that requires encryption (Mailpit doesn't offer it).

## Interview questions

**1. How do you store a one-time code?**
As an HMAC with a server-side secret, bound to the user and purpose, with an expiry and an attempt counter. A plain or salted hash of six digits is reversed in under a second.

**2. Why count the attempt before comparing?**
Otherwise simultaneous requests all see the old count and all get compared. Reserving an attempt atomically first means each request gets its own number.

**3. How do you make a code single-use under concurrency?**
Let one atomic operation decide: a conditional delete that only one request can win. Checking and deleting separately lets two through.

**4. What's account enumeration, and how do you prevent it?**
Finding out which emails have accounts from differences in responses, status codes or timing. Use the same answer and the same code path for both, and make any work that differs happen after the response.

**5. Why a constant-time comparison?**
A normal comparison stops at the first difference, so its duration reveals how much matched. With HMACs an attacker can't choose the stored value, so the risk is small, but the safe version costs nothing.

**6. When do you need Lua in Redis?**
When a decision depends on a value and must be atomic with the change. `MULTI/EXEC` is atomic but can't branch on what it reads. Keep scripts short: Redis runs nothing else meanwhile.

**7. What is Redis eviction, and when do you turn it off?**
At `maxmemory`, Redis can drop keys by policy. Good for caches, wrong for data that exists nowhere else: codes, carts, locks. Use `noeviction` there, and monitor memory.

**8. Liveness, readiness, degraded: where does an optional dependency go?**
If the service can still do useful work without it, report Degraded and keep serving. Failing readiness removes the working part too.

**9. Is email OTP secure?**
It's as secure as the mailbox. It removes password reuse, but can be phished, and delivery can be delayed or intercepted. Passkeys resist phishing. For a food app, email OTP is a reasonable balance.

**10. What's missing before this could go live?**
Rate limits per email and per IP, a real mail provider with required TLS and SPF/DKIM/DMARC, sending through a queue, alerts on failure rates, and key rotation.
